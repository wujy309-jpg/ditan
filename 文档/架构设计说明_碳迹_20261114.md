## 〇、先背会这段（三种时长）

**30 秒版**
> 碳迹是一个单 HAP 的 HarmonyOS 应用，代码分五层：表现层（ArkUI 声明式）、仓储层（Repository）、基础设施层（分布式 KV 封装 + 互斥锁）、端侧 AI 层、领域模型层。最关键的架构决策只有一个：**数据层建在 `distributedKVStore` 上而不是关系库**，因为创新点一是多设备同步，混用两套存储引擎后期必然重写。我们在这之上用「信封 + 最新时间戳优先」实现了真实的冲突策略，用自研互斥锁解决了分布式 KV 没有事务的问题。

**3 分钟版**
> 见「一、架构总览」到「三、六个关键决策」，按顺序讲即可。

**被追问时的一句话兜底**
> 我们的架构目标不是"分层好看"，而是**让三个创新点在数据结构上成立而不是在 PPT 上成立** —— 分布式同步、端侧推理、平台对接，每一个都在数据层有对应的落点。

## 一、架构总览

### 1.1 定性

| 维度 | 结论 |
| --- | --- |
| 形态 | **单 HAP 单体**（不是元服务、不是多 HAP 拆分） |
| 语言/框架 | **ArkTS + ArkUI 声明式**（`@Component` / `@State` / `@Prop`） |
| 分层 | **五层分层**：表现 / 仓储 / 基础设施 / 端侧 AI / 领域模型 |
| 导航 | **单 Ability + 单页面 + Tabs 五页签**，不用 router，不做页面栈 |
| 状态管理 | **纯单向数据流**（`@State` 102 处、`@Prop` 63 处），**不使用 AppStorage / PersistentStorage** |
| 持久化 | **`distributedKVStore`（分布式键值库）**，不用 relationalStore、不用 preferences |
| 第三方依赖 | **仅 1 个**：`@ohos/mpchart@3.0.30`（图表）；所有 UI 组件自绘 |

### 1.3 运行时形态

- **一个 Ability（EntryAbility）** 承载全部界面；
- **一个页面（pages/Index.ets）** 用 `Tabs` 装五个主功能页，**没有页面栈**；
- 两个二级页（`RecordsPage` 行为明细、`YearReportPage` 年度报告）通过页签内部状态切换呈现，不走路由；
- 服务卡片（`CarbonCardAbility`）与备份扩展（`EntryBackupAbility`）是**独立 ExtensionAbility**，与主 UI 无耦合。

> **为什么不做多页面路由**：五个功能是"并列的一本账的五章"，不存在层级导航；引入 router 只会带来返回栈和状态恢复的复杂度，收益为零。

## 三、六个关键架构决策

> 答辩时每条都按「决策 → 理由 → 代价 → 反问」四步讲。

### 决策 1：数据层建在 `distributedKVStore`，而不是 `relationalStore`

- **决策**：全部业务数据存在分布式键值库，键名设计为 `behavior:<id>` / `points:<id>` / `profile`。
- **理由**：创新点 1「超级终端多设备同步」必须直接复用同一套存储引擎。如果先上关系库，后期加同步要重写整个数据层。
- **代价**：KV **没有 where 子句**，查询只能 `keys()` 取全量再内存排序，也没有事务。
- **反问预案**：
  - *"没有 SQL 怎么做统计？"* → 个人级数据量（每天几条到几十条）远未到需要索引的量级；`savedByCategory()` 等统计在内存里做，实测无感知。
  - *"为什么不用关系库 + 自己写同步？"* → 那等于自己实现一套冲突合并，正是分布式 KV 已经解决的问题。

### 决策 2：所有值以「信封」落库 `{ payload, ts, origin }`

- **决策**：任何键写入时都包一层信封，携带业务数据、时间戳、来源设备。
- **理由**：让「最新时间戳优先」（LWW）的冲突策略**真正可落地**，而不是一句空话。没有 `ts` 就无法判断谁新；没有 `origin` 就无法统计远端写入。
- **代价**：每次读要解一层信封，值体积略大。
- **收获**：冲突计数是**真实可信**的 —— 收到远端变更时若本机影子副本更新，判为一次冲突并回写本机版本，`conflictCount` 自增。同步面板上的每个数字都有出处。

### 决策 3：自研 `Mutex` 保护「读-改-写」临界区

- **决策**：积分记账、权益兑换等读-改-写操作用进程内异步锁排队。
- **理由**：分布式 KV **没有事务**。两个并发调用会基于同一份旧值各写一次：**余额只减一次、流水却记两笔**。
- **代价**：必须 `try/finally` 释放，忘记 release 会死锁。
- **诚实边界**（代码注释里写明了）：只保证**同一进程内**的先后顺序；跨设备并发由分布式层负责，**那边同样没有事务，两台真机同时兑换仍可能超卖** —— 这是已声明的不做项，不藏着。

### 决策 4：端侧 AI 双通路，互不依赖、各自降级

- **决策**：MindSpore Lite 视觉分类 与 Core Vision OCR 两条通路并列，任一条失败不影响另一条，两条都失败仍能手动录入。
- **理由**：Core Vision Kit **不支持模拟器**、MindSpore Lite 支持 —— 这是调研得到的硬约束，不是猜测。用户不该因为 AI 挂了就用不了应用。
- **代价**：两条通路都要维护，且结果需要融合策略。
- **实现要点**：即使标定表为空也**总是跑推理**并把 Top-5 打进日志，标定数据就是这样实测出来的，不靠猜。

### 决策 5：城市碳普惠平台用 mock，但保留**全部真实语义**

- **决策**：不接真实接口（未对个人开发者开放），但 mock 保留异步、网络延迟、业务错误码、库存、幂等、账户状态。
- **理由**：路演现场必须离线可用；同时保证"这套代码换真接口只改 transport 层"经得起看代码验证 —— `CarbonInclusiveApi` **只依赖 store，不依赖任何 UI**。
- **代价**：演示时看到的是模拟数据。
- **反问预案**：*"这不是假的吗？"* → 是模拟实现，但对齐了真实接口的语义；真实平台未开放接口，这是唯一诚实的做法，而不是画一个"已对接"的标签。

### 决策 6：零第三方 UI 依赖，表现层自绘

- **决策**：11 个通用组件全部自绘，唯一第三方依赖是图表库 `@ohos/mpchart`。
- **理由**：v2 版本的"渐变英雄卡 + 圆角卡片流 + 胶囊标签"是 AI 生成作品的通用模具 —— **换成蓝色、换掉 logo 依然成立；可替换的界面，在评委眼里就是可替换的作品**。自绘才能做出"这一版账本"的手感（双线表头、引导点线、-5° 手绘朱印）。
- **代价**：组件复用度靠自己做，开发成本高。

## 四、一条数据的完整旅程（端到端）

> 答辩演示时按这条线讲，比讲分层图更有说服力。

```
用户点「保存」
   │
   ▼  EntryPage：inputAmount() 三重边界校验
   │   （非数 / Infinity（1e999）/ 超过上限 AMOUNT_MAX —— 历史上 Infinity 能一路写进账本
   │    并同步到另一台设备，图表上表现为一根顶到天的柱子）
   ▼
CarbonRepository.addBehavior(rec)
   │   ① 生成 BehaviorRecord（活动量 × 因子 = 减排量，因子带 baseline + 出处）
   │   ② 计算应得积分（每 1 kg CO₂e = 100 分）
   ▼
Mutex.lock()
   │   读余额 → 校验 → 写流水，三步在锁内完成，避免并发双记
   ▼
DistributedStore.put('behavior:<id>', 信封{payload, ts, origin})
DistributedStore.put('points:<id>',   信封{payload, ts, origin})
   │
   ▼  分布式层：同一华为账号的其他设备收到变更
   │   LWW 比较 ts → 新则接受；若本机影子副本更新 → 判为冲突、回写、conflictCount++
   ▼
onChange 监听触发 → 看板/积分/我的 三页重新拉取
   │   （KV 无 where，keys() 全量 + 内存排序 + 聚合）
   ▼
图表渲染（mpchart）+ 「我的树」Canvas 重绘（树冠密度 = 累计减排）
```

**这条链路里三个可验证点**（现场可以指给评委看）：

1. 保存时 **Infinity 会被拦截**（不是"理论上"，是实测出来的 bug 修复）；
2. 积分流水与余额**永远对得上**（因为有锁）；
3. 「我的」页的同步面板**能显示冲突次数与远端写入数**（因为信封里真的有 `ts` / `origin`）。

## 五、并发与一致性

| 场景 | 机制 | 保证等级 |
| --- | --- | --- |
| 同进程并发写积分 | `Mutex` 异步锁 | ✅ 严格顺序 |
| 跨设备同时写同一键 | 信封 `ts` + LWW | ⚠️ 最终一致，可能丢一次并发写 |
| 跨设备同时兑换同一权益 | **无事务** | ❌ 可能超卖（已声明的已知限制） |
| 应用被杀时写入中断 | KV 单键原子写 | ✅ 单键不撕裂 |

> **这张表本身就是答辩素材**：主动说出"哪条保证不了"，比等评委问出来强得多。

## 六、端侧 AI 架构

### 6.1 双通路

```
                    ┌─ 通路 A：MindSpore Lite（视觉分类）
图片 PixelMap ──────┤    模型：mobilenetv2.ms（11 MB，随包离线）
                    │    输入 [1,224,224,3] RGB → 输出 [1,500]
                    │    失败 → 保留 OCR 结果
                    │
                    └─ 通路 B：Core Vision Kit（OCR + 关键词）
                         14 条关键词规则
                         失败（**模拟器必然失败**）→ 保留视觉结果
                                     │
                                     ▼
                               fuse() 融合 → AiSuggestion
```

### 6.2 标定表是这套架构的关键设计

模型是 500 类输出、**模型内没有类别标签**，所以「输出索引 → 低碳行为」必须实测：

| 索引 | 映射 | 实测表现（2026-11-13，模拟器内） |
| --- | --- | --- |
| `#347` | 骑行 | 5 张自行车图里 4 张 Top-1，0.981–0.997 |
| `#262` | 旧衣回收 | 3 张里 2 张 Top-1，0.962–0.978 |
| `#292` | 光盘行动 | 6 张里 3 张 Top-1，0.725–0.997 |

**没标定的类别故意留空**（塑料瓶、纸箱、公交、地铁实测 Top-1 只有 0.2–0.3，同类图片之间还乱跳）。硬填进去只会乱预填 —— 让视觉通路对这些类别如实返回"无法判定"，是架构上的诚实。

### 6.3 产品约束

只有**置信度 ≥ 0.5 且因子存在**时才自动预填，否则交给用户确认。这条约束写在 `EntryPage.recognizePixelMap()` 里，是产品设计而非技术细节。

## 十一、答辩预设问答

**Q1：为什么是单体而不是拆分多 HAP / 元服务？**
> 五个功能共享同一份数据与同一套视觉语言，拆分只会带来跨模块状态同步成本。单体 + 内部分层已经让每一层的依赖方向是单向的（view → data → common），未来要拆有清晰的切缝。

**Q2：为什么不用关系库？统计数据怎么算？**
> 见决策 1。个人级数据量在内存里聚合完全够用；`savedByCategory()`、`totalSaved()` 都是内存统计，实测无感知。

**Q3：多设备同步冲突怎么处理？**
> 信封 + 最新时间戳优先（LWW），冲突计数真实可信。**但我要主动说明：跨设备同时兑换权益仍可能超卖** —— 分布式 KV 没有事务，这是已声明的限制，不是遗漏。

**Q4：AI 识别准确率多少？**
> 我不给一个笼统的数字，因为模型是通用 500 类且无标签。实测：自行车的 Top-1 在 5 张图里 4 张命中且得分 0.98+；塑料瓶、纸箱这类实测只有 0.2–0.3，我们**没有硬填标定表**。能力边界比一个好看的数字更值得说。

**Q5：为什么界面不用现成组件库？**
> 见决策 6。v2 的卡片流是可替换的界面，可替换的界面在评委眼里就是可替换的作品。自绘才有"这一版账本"的手感。

**Q6：这个应用联网吗？图片会外传吗？**
> 业务链路完全离线，推理在端侧完成。`INTERNET` 权限只用于一个演示用途：模拟器没有相机，用手机拍照后经局域网把照片送进来再本地推理 —— **图片不出内网、不上云**。

**Q7：代码质量怎么证明？**
> 55 项纯逻辑断言全绿 + 24 个图标自检；关键边界（Infinity 输入、并发双记、ImageSource 资源释放）都是在审计中真发现并修复的，审计报告在工作区 `文档/` 下。

**Q8：如果换成关系库/换框架，要改多少？**
> 只要仓储层接口不变，表现层不用动 —— 因为 `view/` 里没有一行存储驱动代码。这也是我们坚持让页面只调 `CarbonRepository` 方法的原因。

## 附：远程演示链路（不属于应用架构）

> 这一段单独标注，因为它**不是应用的一部分**，是比赛现场的工具。

```
评委手机 ──HTTPS/WSS──► dsh.saidao.asia (nginx) ──location /carbon/──► 反向 SSH 隧道
                                                                          │
                                                              Mac 上的桥接服务
                                                                          │ hdc
                                                              HarmonyOS 模拟器里的碳迹
```

**存在的原因**：HAP 只能在鸿蒙设备上安装，而 OPPO 等 Android 手机装不了。这条链路让评委用自己的手机浏览器就能操作模拟器里的应用，全程不需要安装任何东西。

**性能事实**：帧率上限由电脑端抓帧决定（约 93 ms/帧），公网中转后约 7.2 fps、局域网 8.4 fps。**部署解决可达性，不解决流畅度** —— 这句话建议答辩时主动说，比被问出来好。
