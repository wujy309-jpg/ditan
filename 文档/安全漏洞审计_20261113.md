## 二、逐条说明

### SEC-01 · 系统备份通道默认开启，个人账本可被备份/上云（P1）

**位置**
- `entry/src/main/resources/base/profile/backup_config.json`：
  ```json
  { "allowToBackupRestore": true }
  ```
- `entry/src/main/module.json5:38-50`：`EntryBackupAbility`（`type: "backup"`，`exported: false`）

**边界**：应用沙箱 ↔ 系统备份服务（可能进一步同步到云端）。

**发生了什么**
`allowToBackupRestore: true` 表示应用数据允许被系统备份并参与恢复。应用在 `filesDir` 下写了三类个人数据副本：
- `carbon-backup.json`（`data/CarbonRepository.ets:380-383`，全量行为记录 + 积分流水）
- `carbon-report.csv`（`:386-389`）
- `carbon-share-<ts>.png`（`view/SmartService.ets:370`）

这些文件会随应用数据一起进入系统备份；若用户开启了云备份，**数据就离开了设备**——与本项目「图片不上传、数据不出机」的宣传口径冲突。

**触发条件**：用户设备开启系统备份/云备份（默认多数机型开启）。无需攻击者，属于「设计与宣传不一致」的控制缺口。

**影响**：范围有限（仅本机用户自己的数据），但直接否定产品对外承诺的隐私卖点，答辩被问到时很难圆。

**最小修复**
```json
{ "allowToBackupRestore": false }
```
如果确实需要迁移能力，改为备份前删除导出件、只备 KV 数据：
```json
{
  "allowToBackupRestore": true,
  "exclude_files": ["/files/carbon-backup.json", "/files/carbon-report.csv"]
}
```
（`exclude_files` 的路径写法以目标 API 版本文档为准，改完要用 `hdc shell bm dump` 或系统备份日志确认生效。）

**验证**：改配置 → 触发一次系统备份 → 解包备份产物，确认不含 `carbon-backup.json`。

### SEC-02 · 设备 ID 与平台账号 ID 进公共日志（P1）

**位置**
- `data/CarbonRepository.ets:117`
  ```ts
  hilog.info(DOMAIN, TAG, 'repository ready, localDeviceId=%{public}s', store.getLocalDeviceId());
  ```
- `data/CarbonInclusiveApi.ets:207`
  ```ts
  hilog.info(DOMAIN, TAG, 'account bound: %{public}s', acc.accountId);
  ```
- 同类：`CarbonInclusiveApi.ets:244`（上报请求号）、`:252`（积分总额）、`:348`（订单号）

**边界**：应用 ↔ 系统日志（`hdc hilog`、日志导出工具、部分机型的「用户反馈」日志包）。

**发生了什么**
`%{public}` 明确告诉 hilog「这段不脱敏」。设备 ID 是跨应用可关联的稳定标识，账号 ID（形如 `CP-75627334`）是平台身份，二者组合足以在日志里定位「哪台设备属于哪个账号、减排多少」。

**影响**：需要物理接触设备或开启开发者模式才能读取日志，属于信息泄漏而非越权访问。但这是**零成本可修**的问题，且日志本身对产品没有价值。

**最小修复**：删掉这三条日志，或改成不带标识的描述：
```ts
hilog.info(DOMAIN, TAG, 'repository ready');
hilog.info(DOMAIN, TAG, 'account bound');
```
若要保留排障能力，用 `%{private}`（hilog 会自动打码）。

**验证**：`hdc shell hilog | grep 碳迹TAG`，确认不再出现 64 位设备 ID 与 `CP-` 账号串。

### SEC-03 · 分布式 KV 明文落盘（P2）

**位置**
- `common/DistributedStore.ets:194-200`
  ```ts
  const kvOptions: distributedKVStore.Options = {
    ...
    encrypt: false,
    securityLevel: securityLevel   // 默认 SecurityLevel.S1（:184-185）
  };
  ```
- 存的内容：昵称、家庭 ID、每一条行为记录、积分流水（`data/CarbonRepository.ets` 的 `K_` 前缀键）

**边界**：应用沙箱 ↔ 有 root/调试权限的本机访问者，以及跨设备同步链路。

**发生了什么**
`encrypt: false` 表示 KV 库不加密落盘；`S1` 是最低安全等级。个人碳数据在设备文件系统上是可读结构（JSON 信封）。配合 SEC-01 的备份，数据在「离开应用沙箱」后没有任何加密保护。

**影响**：需要设备被 root 或物理取盘才能读到，属纵深防御缺口，不是独立可利用漏洞。

**最小修复**（二选一）
1. 打开加密：`encrypt: true`，并把 `securityLevel` 提到 `S2`；注意——**开启后旧数据读不出来**，需要写一次迁移（读旧明文 → 写新库）。
2. 明确接受风险：在 `DistributedStore.ets` 头部注释与设计方案里写清「数据仅在应用沙箱内，依赖系统沙箱隔离，未额外加密」，答辩时主动说明，避免被问穿。

**验证**：开启加密后，`hdc file recv` 出 KV 库文件，确认内容为密文且旧数据已迁移。

### SEC-04 · 同步入站数据零校验（P2）

**位置**
- `common/DistributedStore.ets:579` `handleChange()`：解析出 `payload` 后 `this.shadow.set(key, incoming)`（`:624`）并落库
- `common/DistributedStore.ets:287-296`：`getObject()` 直接 `JSON.parse(raw) as T`
- `common/DistributedStore.ets:536-550`：`parseEnvelope()` 只判 `null/undefined`，不校验字段
- 下游消费方：`data/CarbonRepository.ets` 的 `collect<T>()` 同样是 `as T` 强转

**边界**：同账号分布式网络中的**其它设备** → 本机账本。

**发生了什么**
同步链路把对端写入的字符串原样接受，只做「能不能 JSON.parse」的判断，不做任何结构校验。于是：
- 一个被篡改的客户端（同账号、同包名、可写入同一 KV 库）可以推入 `saved: -1e9`、`date: "not-a-date"`、缺失 `id` 的记录；
- 本机刷新时 `total += r.saved` 会把负数/NaN 带进总减排、树冠、年报、积分（`Math.round(saved * 100)`）；
- 更常见的是**版本升级残留**：旧版本写入的字段结构变化后，新版本读到 `undefined` 字段，`formatDate(undefined)`、`sortedDates[0]` 之类会在排序/格式化处产出 `NaN` 或异常。

**影响**：账本被污染后只能 `clearAll()` 重置；跨设备场景下会把坏数据再同步给其他设备。攻击者门槛较高（需要同账号设备 + 篡改包），所以定为 P2 而非 P1。

**最小修复**：在 `handleChange` 落库前，加一个纯函数校验（放 `common/DistributedStore.ets` 或 `data/` 下）：
```ts
function isValidRecord(v: unknown): boolean {
  // 只对已知键前缀做校验；未知键直接丢弃
  // date 必须匹配 /^\d{4}-\d{2}-\d{2}$/
  // saved 必须是有限数且 0 <= saved <= 100
  // id/name/unit 必须是非空字符串且长度受限
}
```
`getObject<T>` 也应在解析后调用对应校验，失败返回 `undefined`（调用方已有 undefined 分支，改动面小）。

**验证**：单测里构造 `{saved: -1}`、`{date: ''}`、缺字段三种 payload，断言被拒绝且账本不变。

### SEC-05 · 数量输入无上限（P2）

**位置**
- `view/EntryPage.ets:294-301`
  ```ts
  const amt: number = Number.parseFloat(this.amount);
  if (!(amt > 0)) { /* 拒绝 */ }
  const saved: number = round2(amt * f.savedPerUnit);
  ```
- `model/Models.ets:142-144` `round2()` 对 `Infinity` 无保护
- `data/CarbonRepository.ets` 积分换算 `Math.max(1, Math.round(saved * POINTS_PER_KG))`

**边界**：输入框 → 账本 →（经同步）→ 对端设备。

**发生了什么**
输入 `1e999` 时 `parseFloat` 返回 `Infinity`，`Infinity > 0` 为真，于是：
- 记录 `saved = Infinity` 落库；
- 积分 `Math.round(Infinity * 100) = Infinity`，余额变成 `Infinity`；
- 卡片、年报、图表全部显示 `Infinity`，且该记录会同步给其它设备；
- `Math.min(320, Math.round(20 + Infinity))` 仍被 320 兜住（`view/DashboardPage.ets:518`），所以不会崩，但数据永久损坏，只能清库。

**影响**：自我污染为主；若演示机同时开了双设备同步，会把坏数据扩散到第二台设备。

**最小修复**
```ts
const amt: number = Number.parseFloat(this.amount);
if (!Number.isFinite(amt) || amt <= 0 || amt > 100000) {
  this.hint = '请输入 0 到 100000 之间的数量';
  return;
}
```
同时在 `round2()` 里加一行 `if (!Number.isFinite(v)) return 0;` 作为兜底。

**验证**：分别输入 `1e999`、`abc`、`-5`、`999999999`，确认全部被拒且账本不变。

### SEC-06 · CSV 导出未转义（P3，前瞻性）

**位置**：`data/CarbonRepository.ets:336-347`

```ts
lines.push(`${r.date},${categoryLabel(r.category)},${r.name},${r.amount},${r.unit},${r.saved}`);
```

**当前是否可利用**：**否**。`name`/`unit` 全部来自 `data/FactorLibrary.ets` 的常量，不含逗号、引号、`=`、`+`、`@`；`amount` 是数字。所以现在只是「一旦支持自定义行为名或备注，就会变成 CSV 公式注入（`=cmd|...`）」。

**建议**：写一个 `csvCell(v: string): string`，`"` 包裹 + 内部 `"` 翻倍，并对以 `= + - @` 开头的值前置 `'`。现在做成本极低，能挡住未来的功能扩展。

---

### SEC-07 · 依赖版本语义（P3）

**位置**：`oh-package.json5:5` `"@ohos/mpchart": "^3.0.30"`

`^` 允许自动升级次版本；仓库里存在 `oh-package-lock.json5`，构建会锁定实际版本，因此**当前风险低**。建议改成 `~3.0.30` 或精确 `3.0.30`，避免有人删了 lock 文件后被动拉新版。

## 四、建议的修复顺序（按今天的时间预算）

1. **SEC-01 + SEC-02**（5 分钟）：改一行 `backup_config.json`、删三条日志。收益最高，且不影响任何功能与截图。
2. **SEC-05**（10 分钟）：输入上限 + `round2` 兜底。防止演示时手滑输入超长数字把账本弄成 `Infinity`。
3. **SEC-04**（30 分钟）：加一个校验函数。演示不依赖它，但答辩被问「同步数据被篡改怎么办」时，这是唯一能拿出来的答案。
4. **SEC-03**（半天，含迁移）：要么开加密，要么在文档里写清边界。**不要在没做迁移的情况下直接打开 `encrypt`**，会导致已录数据全部读不出。
5. **SEC-06 / SEC-07**：有余力再做。

## 五、答辩口径（被问「你们的安全性怎么保证」）

> 我们的安全模型是「数据不出设备 + 最小权限」：
> 1. 应用**没有申请网络权限**，全部计算在本机完成，图片识别结果不上传；
> 2. 对外只暴露桌面入口和一张卡片，没有自定义 scheme，不能被第三方应用调起；
> 3. 账本存在应用沙箱内的分布式 KV 里，不写公共目录；
> 4. 我们做过一次针对自身代码的安全审计（就是这份报告），把「系统备份会把导出件带走」「设备 ID 进了公共日志」这类问题都改掉了——**这是评委很少听到的回答，因为它说明我们真的按攻击者视角看过自己的代码**。

如果被追问「那加密呢」：如实说「当前依赖系统沙箱隔离，未额外加密；如果要上生产，第一件事是打开 KV 加密并做一次数据迁移」。
