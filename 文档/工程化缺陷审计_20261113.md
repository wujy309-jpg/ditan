### ENG-01 · 打包脚本会把「附加讲解视频」一起打进提交 rar（P1）

**位置**：`tools/package.sh:53-67`

```bash
videos=("$DELIV"/*.mp4)
...
for v in "${videos[@]}"; do
  ...
  cp "$v" "$STAGE/"
```

**证据**：`交付物/` 下有两个 mp4——
- `演示视频_碳迹.mp4`（15.6 MB，1′52″，**正式评审用**）
- `演示文稿_讲解视频.mp4`（17.4 MB，4′52″，清单里标注「附加材料，不进评审包」）

glob 会把两个都收进去。

**影响**：提交包与《提交信息与检查清单》口径不一致；评审包多出 17 MB 未声明内容，评审若按「包含三项材料」核对会认为多交了东西。视频总时长也可能被合并计算。

**修复**：改成白名单，只认那一个文件名：
```bash
videos=("$DELIV/演示视频_碳迹.mp4")
```
或加参数 `--video <文件名>`，默认取「演示视频_碳迹.mp4」。顺手补一条「时长 ≤5 分钟」的提示（脚本现在只查 100MB 体积，不查时长）。

**验证**：跑一次 `tools/package.sh`，`unrar l` 检查暂存目录里只有一个 mp4。

### ENG-02 · 脚本仍绑定 macOS（P1）

**证据（三处，按危害排序）**

1. `tools/build.sh:40` —— **写死且不可覆盖**：
   ```bash
   (cd "$DST" && /Applications/DevEco-Studio.app/Contents/tools/ohpm/bin/ohpm install)
   ```
   在 Windows/Linux 上必然 `No such file or directory`，且脚本没有候选路径查找。
2. `tools/package.sh:59` —— **BSD `stat` 语法**：
   ```bash
   size_mb=$(( $(stat -f%z "$v") / 1024 / 1024 ))
   ```
   GNU coreutils / Git Bash 上 `stat -f%z` 取不到值 → 算术表达式为空 → `set -e` 直接中止（或算出 0 后误判体积）。
3. `tools/device.sh:28`、`tools/emulator.sh:26` —— 默认值写死 macOS 路径：
   ```bash
   DEVECO_APP="${DEVECO_APP:-/Applications/DevEco-Studio.app}"
   ```
   这个**可以**用环境变量覆盖，危害低于前两条，但默认值会误导人。

**影响**：`test-logic.sh` 的同类问题上一轮已修（改为多平台候选 + `CARBON_TSC` 覆盖），但**只修了一处**。队友在 Windows 上执行 `build.sh` / `package.sh` 会直接失败，而这两个恰好是提交前必跑的。

**修复**：抽一个 `tools/_env.sh`，集中做「DevEco 安装目录候选查找 + 可执行文件探测 + stat 兼容」三件事，其余脚本 `source` 它。`stat` 用 `wc -c <"$f"` 这种跨平台写法最稳。

**验证**：在 Windows Git Bash 里 `source tools/_env.sh` 后打印 `DEVECO_APP`、`OHPM_BIN`、`STAT_SIZE(file)`，三者都有值。

### ENG-16 · 声明了分布式权限却从不申请，真机上「超级终端同步」静默失效（P1，补录）

> 这条是本报告第一版的遗漏，由团队指出后补入。遗漏原因写在文末「补录说明」里。

**位置**
- `entry/src/main/module.json5:70-85`：声明了 `ohos.permission.DISTRIBUTED_DATASYNC`，注释自己就写着「属于 user_grant（运行时需用户弹窗授权）」；
- 全工程 `grep -rn "requestPermissionsFromUser|abilityAccessCtrl|verifyAccessToken"` → **零命中**；
- `common/DistributedStore.ets:227`：`instance.subscribeChange()` 只在建库时调用一次；
- `common/DistributedStore.ets:439-452`：订阅失败只 `hilog.warn` 并把 `changeSubscribed = false`；
- `common/DistributedStore.ets:340-347`：`sync()` 在 `!changeSubscribed` 时直接返回 `NO_PEER`；
- `view/ProfilePage.ets:62-63`：`NO_PEER` → 文案「无可信设备」；`:168-171`：`localOnly` → 「本机模式 · 跨设备同步不可用」。

**三层问题，一层比一层隐蔽**

1. **从不申请**：`user_grant` 权限默认是拒绝状态，不调用 `requestPermissionsFromUser` 就永远拿不到。`distributedDeviceManager.createDeviceManager` 与 `kvStore.on('dataChange')` 都会因缺权限失败。
2. **授权状态只采样一次**：`subscribeChange()` 只在 `DistributedStore.create()` 里跑一次。即便用户事后去「设置 → 应用 → 权限」手动打开，也要**杀掉进程重开**才会重新订阅——这条降级是「粘滞」的。
3. **三态被压成一态**：面板把「没授权」「查不到设备」「订阅失败」全部显示成「本机模式 / 无可信设备」。用户和评委都看不出区别，也没有任何「去授权」的引导。

**影响**
创新点 1（超级终端同步面板 + 双设备同步）在真机上**一次都不会出现**。更麻烦的是降级路径写得很优雅——不崩溃、不白等 15 秒、面板安静显示「本机模式」——恰恰让这个缺陷极难在开发阶段被发现。演示视频若要拍双机同步，会在现场翻车。

**修复（已改入代码，未经编译验证）**

`view/ProfilePage.ets:284` 新增 `ensurePermission()`，`doSync()`（第 303 行）在 `repo.syncNow()` 之前插入两步：

```ts
const atManager: abilityAccessCtrl.AtManager = abilityAccessCtrl.createAtManager();
const perms: Permissions[] = ['ohos.permission.DISTRIBUTED_DATASYNC'];
const res = await atManager.requestPermissionsFromUser(rawCtx as common.Context, perms);
if (!(res.authResults.length > 0 && res.authResults[0] === 0)) {
  this.msg = '未授予「分布式数据同步」权限，跨设备同步不可用';
  return;
}
repo.retrySubscribe();   // 关键：重订阅，否则本次运行仍是单机模式
```

`common/DistributedStore.ets:463` 与 `data/CarbonRepository.ets:416` 新增 `retrySubscribe(): boolean`，把 `subscribeChange()` 重新跑一遍并返回结果。顺序不能反：没订阅成功时 `sync()` 会直接返回 `NO_PEER`，白跑一趟。

面板文案建议拆成三态：`未授权`（引导点同步按钮）、`已授权 · 无对端设备`、`已连接 N 台`。

**验证（必须在真机上做，模拟器不算）**
1. 卸载重装 → 点「同步」→ 应弹出系统授权框；
2. 选「允许」→ 面板从「本机模式」变为真实设备列表；
3. 选「拒绝」→ 面板明确显示「未授权」，且不出现误导性的「无可信设备」；
4. 拒绝后去设置里手动开启 → 回到应用点同步，**不重启也应生效**（这是 `retrySubscribe` 的存在意义）。

**演示前置条件（写进答辩手册）**：两台设备登录**同一华为账号**、安装**同一签名的包**、互相出现在「可信设备」列表、两边都授权。

### ENG-04 · 13 处 `this.refresh()` 没有 await / 没有 catch（P2）

**位置**

| 文件 | 行号 |
| --- | --- |
| `view/DashboardPage.ets` | 118、122、782 |
| `view/EntryPage.ets` | 97、101 |
| `view/PointsPage.ets` | 95、99 |
| `view/ProfilePage.ets` | 115、119 |
| `view/SmartService.ets` | 260、264 |
| `view/YearReportPage.ets` | 203、207 |

**发生了什么**：`refresh()` 是 `async`，内部 `await repo.pointsBalance()`、`await repo.listBehaviors()` 等都可能抛（KV 未就绪、put/get 失败）。调用处既不 `await` 也不 `.catch()`，于是变成 unhandled promise rejection——hilog 里一行红色堆栈，**界面上什么都不会说**，数字停在初始值 0，用户以为数据丢了。

**影响**：不是数据错误（数据还在 KV 里），是**可观测性缺失**：故障态和「今天还没记账」长得一模一样。演示时若 KV 恰好没起来，画面就是一片 0，没有任何提示。

**修复**：在六个页面统一成
```ts
private async refresh(): Promise<void> {
  try { /* 原有逻辑 */ }
  catch (e) { this.errMsg = '数据读取失败，下滑重试'; }
}
```
调用处保持 `this.refresh();` 也无妨（内部已兜住）。`Index.boot()` 已有 `errMsg` 模式，可复用同一套文案风格。

**验证**：临时让 `repo.markReady()` 前的刷新先跑（或 mock 一次 throw），确认界面出现错误文案而不是 0。

### ENG-07 · 测试覆盖偏科（P2）

**现状**：`tests/logic.test.ts` 只 import 四个模块——
`model/Models`、`data/FactorLibrary`、`data/TaskEngine`、`common/RoughMath`。

**零覆盖的恰恰是最容易出事的三个文件**：`data/CarbonRepository.ets`（370 行）、`common/DistributedStore.ets`（655 行）、`data/CarbonInclusiveApi.ets`（340 行）。上一轮修的「删记录不回滚积分」「addPoints 负数透支」「上报不幂等」「影子副本顺序」全在这三个文件里，全部靠人工推演 + 一次 Mutex 模拟验证，没有回归保护。

**修复**：这三个类的依赖是 `store`（KV 封装）与 `delay`，都可以注入假实现。抽一个 `FakeStore`（内存 Map 实现 `get/put/delete/getObject/getEntries`），就能把 Repository 的 6 条不变量写成断言：
- 删记录后余额回到删除前
- `addPoints(-余额-1)` 返回 `delta === 0` 且不落流水
- 同 `requestId` 上报两次只计一次
- `addBehavior` 在 addPoints 抛错时不留记录
- `collect()` 分批读取结果顺序与键顺序一致
- `init()` 并发调用只建一个 store

**验证**：这些断言在 `node --experimental-transform-types` 下可跑（FakeStore 不依赖 ArkUI）。

## 附二：ENG-16 为什么第一版漏了

第一轮安全审计时我把它归到「功能缺口」而不是「漏洞」——原话是「未申请运行时权限——功能/兼容，不是漏洞」。这个判断本身没错：它确实不构成安全风险，甚至相反（少一个权限声明更安全）。

问题出在第二轮的起点：工程化审计是从**构建配置、打包链路、脚本**往外扫的，扫完 `module.json5` 的 `requestPermissions` 就接着看 `app.json5` 的 vendor，没有回头核查「声明了的东西有没有被使用」。于是它正好卡在两份报告的接缝上，两边都没收。

方法上的教训值得记下来：审计工程本体时，除了看「配了什么」，还要专门扫一遍**「配了但没接上的」**——声明了权限却从不申请、声明了 exported 却没有入口、ignore 了不存在的目录。ENG-08（`RingStat` 全工程零调用）和 ENG-06（`code-linter.json5` ignore 两个不存在的目录）其实是同一个模式的另外两个样本，只是它们没这么致命，所以当 P3 处理了。
