**第一层 · 一句话（10 秒，任何人问「你们做了什么」都用它）**

> 我们把「今天省了多少碳」做成一本人人看得懂、记得住、能换东西的账本——一笔一笔记、一页一页算、一年一册收，数据不出手机。

**第二层 · 三个锚点（评委离场后能复述的三个词）**

## 1. 项目定位：它到底是什么，不是什么

### 1.1 问题定义（这是整套设计的起点，务必讲清）

个人碳减排产品的死结不是「算不出来」，而是**算出来没人愿意记**。原因有三个：

1. **不可核**：网上随手一个「步行 1 公里减碳 0.2 kg」，没有基准情景、没有出处，用户不信，评委也不该信。
2. **不可感**：kg CO₂e 是个抽象数。人对「20.58 公斤碳」没有体感，但对「1.1 棵树一年」「2058 积分能换张地铁票」有体感。
3. **不可持续**：记录一次要 5 步以上，第三天就放弃。

我们的三个对策，正好对应三个创新点：

| 死结 | 对策 | 落地形态 |
|---|---|---|
| 不可核 | 因子库工程化：每条因子带基准情景、单位、来源、口径说明 | 应用内「数据出处」可展开；`FactorLibrary.ets` 头部有完整选型论证 |
| 不可感 | 双重转译：kg → 棵树·年（÷18）；减排 → 积分（×100） | 看板「我的树」随减排长大；积分页可兑地铁券 |
| 不可持续 | 把「记一笔」压缩到 2 步，并让 AI 预填 | 首页直接是记一笔表单；拍照/选图自动识别类目 |

### 1.2 明确「不是」

答辩时主动划边界，比被问出来强：

- **不是碳交易平台**：不做配额、不做 CCER，不涉及任何金融属性。
- **不是企业碳盘查工具**（GHG Protocol 那套范围一/二/三），我们是**个人消费端**核算。
- **不是社交产品**：没有排行榜、没有好友，因为碳数据一旦社交化，必然出现攀比和伪造。
- **不是城市碳普惠的替代品**：城市平台是模拟实现，接口语义（错误码、幂等、库存）对齐真实平台，接真接口只需替换 transport 层。

### 1.3 用户与场景

- 主用户：25–40 岁城市通勤者，有环保意愿但缺正反馈。
- 高频场景：通勤（步行/骑行/地铁/公交/新能源）、居家（节电/节水）、回收（塑料/纸/铝/衣物）、餐饮（光盘）。
- 低频但有仪式感的场景：看年度报告、兑换权益、生成减排凭证。

## 2. 创作思路：为什么长成「一本账」

这一节是**设计分**的核心。评委问「为什么不用常见的卡片式界面」时，用下面这条论证链回答，不要说「因为好看」。

### 2.1 论证链（四步，缺一步就变成审美偏好）

1. **产品的本质是记账**，不是仪表盘。记账的心理模型是「一笔一笔、可追溯、要对得上」，仪表盘的心理模型是「一眼看趋势」。
2. **记账的视觉原型是账本**：纸、横线、手写体标题、红色印章确认。它自带「可信、留痕、私密」三个属性。
3. **卡片流会破坏账感**：圆角+投影+白底意味着「一个个独立的信息块」，视觉上把连续的数据切成碎片，读起来像资讯流而不是账。
4. **所以规则是**：不用卡片、用 1px 细线分组；圆角一律 2；阴影全透明；朱砂红是唯一高饱和色且面积不超过 2%（它只用来做印章、强调、危险提示）。

### 2.2 设计令牌（被问「你的设计系统是什么」时直接报）

| 类别 | 取值 | 用法 |
|---|---|---|
| 纸 | `#F2EDE1` / `#FBF8F1` | 页底 / 卡片底（卡片只在必要处出现） |
| 墨 | `#201D17` / `#4C463A` / `#857C6A` / `#B5AC98` | 四级文字层级 |
| 朱砂 | `#AB3A28` | 印章、警示、选中态，面积 ≤2% |
| 绿 | 品牌绿（`Brand.PRIMARY`） | 正向数据、成功态 |
| 圆角 | 2 | 全站唯一值 |
| 阴影 | `radius:0, color:Transparent` | 全站禁用 |
| 字体 | 标题 Noto Serif CJK SC（1176 字子集，546 KB，SIL OFL 1.1）；正文黑体 | 宋体只做标题与数字，正文不上宋体（小字号宋体在手机上会糊） |
| 数字 | `fontFeature('"tnum" 1')` | 等宽数字，账目对齐 |

> 补充一个能加分的工程细节：我们没用系统宋体，而是**子集化内嵌**。系统字体各家不同（有的设备根本没有衬线中文字体），账本一旦字体回退就崩。子集只保留 1176 个用到的字，546 KB，可接受。

### 2.3 反常识的三个决定（每个都能引导一个提问）

1. **不用图标库，24 个图标全部矢量重绘**，并用脚本统一视觉重量（极差 0.34%）——因为混用第三方图标会出现线宽、圆角、视觉重心不一致，账本对这点极敏感。
2. **图表关掉一切交互**（不可缩放、不可拖拽、不可点选、无图例）——图表在这里是「信息图」不是「分析工具」，交互会让它从账页变成控件。
3. **不用渐变面积填充**——v2 曾用「30% 绿→透明」的面积渐变，被我们自己否掉：账本记线，不记雾；而且零数据时那片渐变比空白更难看。

## 3. 信息架构与用户动线

五个页签，对应账本的五个动作：

```
记一笔（记账）── 看板（对账）── 积分（兑换）── 科普（读账）── 我的（档案/导出/同步）
        └────────────── 年度报告（年终总结，从看板进入）──────────────┘
```

**一次「记一笔」的完整链路（评委问「点保存之后发生了什么」时按这个顺序讲）**

1. 用户选类目 → 选行为 → 填数量（单位随因子变：公里/度/立方米/公斤/餐次）。
2. 实时预览：`数量 × savedPerUnit`，显示「本次减排 1.17 kg CO₂e」。
3. 保存 → `CarbonRepository.addBehavior()`：先写行为记录（behavior 键），再按 `saved × 100` 发放积分（points 键）。
4. 若积分写入失败，**回删行为记录**——宁可整笔不成立，也不留「有账无分」的哑账。
5. 成功后刷新本页（累计/今日/本周/最近记录），并通知桌面卡片刷新（卡片刷新失败不影响记账成功，单独 try/catch）。
6. 切到看板时，页面 `@Watch` 数据版本号触发刷新，重算树、热力图、折线、分类占比、今日任务。

> 关键设计：**刷新靠版本号而不是路由生命周期**。ArkUI 的 TabContent 是预建的，`aboutToAppear` 只跑一次，所以页签切换时数据不会自动更新。我们在 Index 里维护 `dataVersion`，每次切页签 +1，各页 `@Prop @Watch('onVersion')` 接住。这是一个真实踩过的坑。

### 4.1 分层

```
┌ view 层（7 个页面 + 图表 + 通用组件 + 智能服务）
│   EntryPage / DashboardPage / PointsPage / KnowledgePage / ProfilePage / YearReportPage
├ 状态与能力层
│   pages/Index.ets（导航 + 数据版本 + 字体注册）
│   view/SmartService.ets（今日任务、凭证、导出、分享）
├ 数据层
│   data/CarbonRepository（行为、积分、档案、导出、沙箱写文件）
│   data/CarbonInclusiveApi（城市碳普惠模拟：绑定/上报/权益/兑换，带错误码与幂等）
│   data/TaskEngine（今日任务与建议引擎）
│   data/FactorLibrary（14 条因子 + 出处论证）
│   data/KnowledgeBase（8 篇科普）
├ 平台层
│   common/DistributedStore（分布式 KV 封装：影子副本、变更订阅、冲突收敛）
│   common/Mutex（进程内异步互斥）
│   entryability（应用入口）、cardentry（桌面卡片）
├ AI 层
│   ai/MindSporePredictor（MobileNetV2 推理）
│   ai/LowCarbonClassifier（视觉 + OCR 双通路编排）
│   ai/CategoryMapping（类别映射、融合、标定表）
│   ai/AiSelfCheck（模型自检）
└ 几何与主题
    common/Theme（设计令牌）、common/RoughMath（抖动几何，纯 TS 可测）
```

### 4.2 为什么这么分（一句话一层）

- **view 不含业务计算**：页面只负责「取数 → 摆位置」，所有数值来自 repository 或 TaskEngine，这样 55 条逻辑断言可以在没有 UI、没有设备的情况下跑。
- **数据层不碰 UI 类型**：`common/RoughMath.ets` 这类纯计算模块**禁止 import ArkUI 类型**，否则 Node 里跑不了测试。
- **平台层不假设网络存在**：每个 KV 调用都 try/catch 后包成 `Error` 抛给业务层，业务层决定降级还是提示。

## 5. 知识点一：碳核算方法学（最容易被专业评委考的地方）

### 5.1 核心公式

```
ER = AD × (EF_baseline − EF_activity)

ER          减排量 kg CO₂e（我们库里 savedPerUnit 就是这个差值）
AD          活动量（公里 / 度 / 立方米 / 公斤 / 餐次）
EF_baseline 基准情景排放因子（如果不做这个低碳行为，会排放多少）
EF_activity 实际行为排放因子（做了之后排放多少）
```

**最容易问倒人的一句话**：「你们算的是减排量还是排放量？」

> 答：算的是**减排量**，即「基准情景 − 实际情景」的差值。库里每个值都是差值，`baseline` 字段写明基准情景是什么（例如步行/骑行的基准是「燃油小汽车 0.19567 kgCO₂e/车·公里」）。如果用户本来就不开车，这个减排量严格说是「假设性减排」，这也是国际通行的算法——碳普惠、CCER 都用同一逻辑。

### 5.2 14 条因子全表（必背前 5 条，其余记来源）

| # | 行为 | 单位 | 减排因子 kg CO₂e | 数据来源 |
|---|---|---|---|---|
| 1 | 步行 | 公里 | 0.19567 | CPCD 2023，基准＝燃油小汽车 |
| 2 | 骑行 | 公里 | 0.19567 | 同上 |
| 3 | 地铁出行 | 公里 | 0.15253 | CPCD，取「实际人公里」43.14 g − 基准 |
| 4 | 公交出行 | 公里 | 0.14267 | CPCD |
| 5 | 新能源车 | 公里 | 0.02567 | CPCD + 电网因子 |
| 6 | 节约用电 | 度 | 0.5897 | 生态环境部 2023 年电力因子公告·表 3 河南 |
| 7 | 少开空调 | 度 | 0.5897 | 同上 |
| 8 | 节约用水 | 立方米 | 0.36218 | DEFRA 2025（中国无对应官方因子） |
| 9 | 回收塑料 PET | 公斤 | 0.3208 | CPCD |
| 10 | 回收废纸 | 公斤 | 0.2197 | DEFRA 2025 |
| 11 | 回收易拉罐（铝） | 公斤 | 8.1208 | DEFRA 2025 |
| 12 | 回收旧衣物 | 公斤 | 22.1578 | DEFRA 2025 |
| 13 | 光盘行动 | 餐次 | 0.19 | 中科院地理所 + WWF《中国城市餐饮食物浪费报告》2018 |
| 14 | 减少食物浪费 | 公斤 | 2.06 | FAO《Food Wastage Footprint》2013 |

### 5.3 数据来源的四级优先（这段讲好了直接拉分）

1. **中国本土优先**：CPCD（中国产品全生命周期温室气体排放系数库）。
2. **官方公告其次**：生态环境部、国家统计局《2023 年电力二氧化碳排放因子公告》（2025 年第 47 号）。
3. **国际权威兜底**：DEFRA 2025（英国环境、食品和农村事务部）——中国官方没有的条目才用，且**在应用里逐条标注「英国口径」**。
4. **学术报告补充**：中科院 + WWF 餐饮浪费报告、FAO。

### 5.4 三个「坑」（评委如果懂行，一定从这里切）

**坑 1：生态环境部《大型活动碳中和实施指南（试行）》里没有任何排放因子数值。**
它只给「排放源 → 该用哪份标准」的对照表。网上大量教程说「因子出自这份指南」，是错的。它的正确用途是**合规性依据**——证明我们的因子选型体系符合生态环境部推荐路径。

**坑 2：《省级温室气体清单编制指南》没有「每人公里」交通因子。**
它是区域清单方法学，道路交通算的是「全省分燃料消费量 × 单位热值含碳量 × 碳氧化率」。拿它的表去当出行因子用，是典型的口径错配。

**坑 3：CPCD 的地铁因子有两个条目，相差 4.9 倍（8.81 与 43.14 gCO₂e/人·公里）。**
我们取 43.14（名为「实际人公里」），因为它的量级与京沪地铁实际值、DEFRA 伦敦地铁（27.8 g）更吻合；8.81 明显偏离。**在小库里必须选一个并说明理由**，否则地铁减排量会虚高。

### 5.5 已知口径边界（主动说，别等人问）

- 出行基准按**单人驾车**计，「车·公里」= 「人·公里」；多人共乘时人均应除以乘员数，我们**没做**这个折算，应用内已说明。
- 电网因子用**河南省**省级值（比赛在河南），不是全国平均 0.5306；两者都写在出处里。
- 电力因子同一公告内有 5 个口径，数值差异最大 56%，我们固定用「表 3 省级」。
- 4 条回收/水务因子是英国口径（DEFRA），中国无官方对应值。

> **杀手级回答**（被问「你们的数据可靠吗」）：
> 「可靠性的关键不是数字精确到小数点后几位，而是**每个数字都能追到一份公开文件、并说明为什么选它**。我们把这件事写进了代码注释和应用内的数据出处页——包括我们选了哪个口径、放弃了哪个、为什么。同样是 0.15253 的地铁因子，别人说不出来源，我们能说出 CPCD 两个条目相差 4.9 倍以及我们为什么取大的那个。」

## 6. 知识点二：HarmonyOS 平台能力（技术分的主战场）

### 6.1 用了哪些系统能力（按「评委可能问」排列）

| 能力 | 用在哪 | 一句话解释 |
|---|---|---|
| 分布式键值数据库 `distributedKVStore` | 全部业务数据 | 同一份数据在组网设备间自动同步，本机读写不依赖网络 |
| 分布式设备管理 | 可信设备列表 | 列出同账号组网设备，用 deviceId 判断「是不是自己人」 |
| 桌面卡片（Form / EntryFormAbility） | 桌面小组件 | 不打开应用也能看到今日减排与积分 |
| MindSpore Lite | 端侧图像分类 | 11.4 MB 的 MobileNetV2，本机推理，图片不上传 |
| Core Vision Kit 文字识别 | 端侧 OCR | 识别小票/账单文字，补充视觉模型的判断 |
| ArkUI 声明式 UI + Canvas | 全部界面与「我的树」 | 自绘矢量图形，不依赖图片资源 |
| 字体注册 API | 账本宋体 | `getUIContext().getFont().registerFont()`（旧的 `font.registerFont` 已废弃） |
| 沙箱文件读写 | JSON 备份、CSV 导出 | 数据可带走，不用云 |

### 6.2 分布式 KV 的四个关键设计（这是「技术深度」的落点）

**① 键空间设计**：所有业务键带前缀（`K_BEHAVIOR` / `K_POINTS` / `K_PROFILE` / `K_STOCK` …），同步时按前缀过滤，避免把别人的键拉进来。导出包有 `schema: 'carbon-footprint/v1'` 字段——**版本化意识**，将来改结构能识别老包。

**② 影子副本（shadow）**：本地维护一份内存镜像，读优先读影子，写先落 KV 再更新影子。为什么？分布式 KV 的读是异步的，UI 需要同步可用；且同步冲突时能拿本地版本比对。
> 这里修过一个真实 bug：原实现**先写影子再写 KV**，KV 写失败时影子已经含有未落库版本，后续冲突处理会把幽灵版本回写，数据"复活"。现在改成先 KV 后影子。

**③ 冲突收敛：Last-Write-Wins + origin 兜底**
- 比较两个信封的 `ts`（写入时间戳），大的赢。
- `ts` 完全相等时，比较 `origin`（设备标识）做确定性兜底，避免两边互相覆盖形成震荡。
- 同版本回声直接短路（`ts` 与 `origin` 都相同 → 跳过），否则自己的写入会被当成远端更新反复处理。

**④ 变更订阅与降级**
`kvStore.on('dataChange')` 在部分环境（预览器、未授予分布式权限的设备）会失败，且抛出的错误连 code/message 都是空的。**订阅失败只意味着收不到远端变更，本机读写完全正常**，所以降级为「本机模式」，UI 上把「可信设备」显示为「本机模式 · 跨设备同步不可用」，而不是整屏报错。

> **被问「你的同步怎么保证一致」**：
> 「单机内用互斥锁保证顺序，跨设备用 LWW + origin 确定性收敛。我们不假装有强一致——分布式 KV 没有事务，跨设备同时兑换理论上仍可能超卖。这是我们写明的边界，真正的解法是服务端幂等键，而不是在端上堆锁。」

### 6.3 状态管理与 ArkUI 的坑（这些细节说明「真写过」）

- **TabContent 预建**：`aboutToAppear` 只跑一次 → 用数据版本号 + `@Watch` 驱动刷新。
- **`@Builder` 按值传参不重绘**：依赖状态的子视图必须改成 `@Component` + `@Prop`。
- **Button 默认 Capsule**：不写 `type: ButtonType.Normal`，`borderRadius` 会被忽略。
- **`backgroundColor` 会盖住 `backgroundImage`**，纹理只能挂根节点或用 `backgroundImageSize`。
- **`$rawfile` 不能当背景**，必须 `$r('app.media.x')`。
- **`Path().commands()` 单位是 px 不是 vp**——跨设备会错位。
- **矩形 + rotate + position 拼树会渲染成三棵树**（每个子节点各自旋转），所以「我的树」改用 Canvas 自绘。
- **Stack 是叠放不是竖排**。
- **mpchart 的 `Fill` 至少要两个色标**：`new Fill([一种颜色])` 不报错，但柱子会画成纯黑（实测）。

## 7. 知识点三：算法与技巧（创新分的主战场）

### 7.1 端侧 AI：三路信号 + 融合决策

**整体流程**

```
用户拍照/选图
   ↓
uriToPixelMap()            解码成 PixelMap（用完必须 release）
   ↓
┌──────────────┴──────────────┐
视觉通路                        文字通路
MobileNetV2 (224×224)          Core Vision Kit OCR
→ 1000 维 logits               → 文本行
→ 与标定表里的类别中心向量比较      → 14 条关键词规则匹配
→ top-5 类别 + 置信度            → 命中即给 0.75 置信
└──────────────┬──────────────┘
          fuse() 融合
   ↓
置信度 ≥ 0.5 且因子存在 → 自动预填类目与行为
否则 → 只给提示，交用户手选
```

**三路信号怎么融合（这是被问「你的算法是什么」时的正解）**

- 若视觉与 OCR 指向**同一类目**：置信度加权提升（相互印证）。
- 若**冲突**：取置信度更高的那一路，但**乘 0.6 降权**，并在界面上提示「建议确认」——冲突本身就是信息，不能当成确定结论。
- 若只有一路：直接用，但低于 0.5 不预填。

**标定表（Centroid 分类）的原理**：把 MobileNetV2 当特征提取器，对每个类别采集若干张真实照片，输出 logits 求均值作为「类别中心向量」；推理时算余弦相似度取 top-k。好处是**不需要重新训练模型**，采几十张照片就能扩类；坏处是它依赖真实照片——这也是下面这个敏感点的来源。

**⚠️ 必须如实交代的事实（这是全场最高危问题）**

当前交付版本 `ai/CategoryMapping.ets` 的 `INDEX_TO_FACTOR` 是**空表**，所以：
- `visionReady()` 返回 false，视觉通路**不会**产出建议；
- 实际生效的是 OCR 关键词匹配（14 条规则，命中给 0.75 置信）；
- 模型加载、预处理、推理、自检这些代码都是真实可运行的（「我的」页有端侧 AI 自检入口，能跑出 top-k），但**在拿到真机标定照片之前，视觉结果不参与业务判断**。

**怎么答才不失分**（建议照这段说，别绕）：

> 「我先把边界说清楚：模型和推理链是真的，MobileNetV2 通过 MindSpore Lite 在端侧跑，自检页能看到真实的 top-5 输出；但分类标定表现在是空的，因为它需要真机拍的真实照片才能建类别中心，模拟器摄像头喂不了这类样本。所以当前版本走的是 OCR 关键词兜底——这是有意的降级，不是伪装成 AI。工程上我们做的是『模型可插拔 + 缺样本时优雅降级』：填表之后视觉通路自动生效，业务代码一行不用改。下一步计划是采 200 张真实照片、6–8 类，做端侧标定。」

这个回答的好处：承认边界 → 展示工程判断 → 给出可执行下一步。评委扣不了分，因为你在用工程师的方式说话。

### 7.2 今日任务引擎（`data/TaskEngine.ets`）

**三个输入**：用户的记录、因子库、当前日期。
**三个输出**：今日任务（3 条）、建议（3 类）、一句话总结。

**任务挑选是一个多目标排序**：

1. **未完成优先**：今天已经做过的类目降权，避免推荐重复动作。
2. **短板优先**：算各分类的累计占比，占比最低的分类优先补。
3. **补足 3 条**：不足则从剩余因子按「单位减排量 / 操作成本」补。

**建议引擎三段式**：

- 趋势对比：近 7 天 vs 前 7 天，上升/下降给不同话术。
- 短板提示：哪个类目占比过低，给一条具体可做的行为。
- 停留提醒：最后一次记录距今天数 ≥2 天时，提醒「你已经 3 天没有记账」。

> 这里修过一个隐性契约 bug：原实现直接用 `records[0].date` 当「最近一次」，隐含假设调用方已按时间倒序传数组。现在改为遍历取最大日期，调用顺序不再影响正确性。

### 7.3 积分账本：一致性的三道防线

**规则**：每减排 1 kg 发 100 分（`POINTS_PER_KG = 100`）。日记账每条流水记录 `delta`、`reason`、`ts`、`balanceAfter`。

**防线 1 · 事务补偿**
`addBehavior` 先写记录再发积分；积分失败则**回删记录**并抛错。杜绝「账上有记录、积分里没有」。

**防线 2 · 撤销而非删除**
删除一条记录时，按当初发放规则（`max(1, round(saved × 100))`）算出应撤销额，写一条负数流水「撤销「步行」」。**不是把流水删掉**——账本不能有涂改，只能有冲正。
且撤销额不超过当前余额（已花掉的追不回），保证 `balanceAfter` 算术自洽。

**防线 3 · 余额保护 + 互斥**
- `addPoints` 全程持锁（`common/Mutex.ets`，Promise 链式串行）。
- 若 `delta < 0` 且余额不足，**拒绝落账**，返回 `delta = 0` 的哨兵，调用方据此提示「积分不足」。
- 效果：双击兑换按钮不会扣两次，余额也不会变成负数。

**为什么用自研 Mutex 而不是别的**：ArkTS 侧没有现成的跨 await 互斥；实现是 `tail: Promise` 链，`lock()` 返回 `release` 闭包，**必须 try/finally 释放**（忘记会死锁），注释里写明了这一点。实测 50 个并发 worker 抢临界区，`counter=50`、最大并发=1；去掉锁的反证版 `counter=1`（丢 49 次更新）。

### 7.4 城市碳普惠：把「模拟」做成「可替换」

虽然不连真平台，但我们按真实平台的语义实现：

- **错误码体系**：`NOT_BOUND 1001` / `INSUFFICIENT 1002` / `OUT_OF_STOCK 1003` / `NETWORK 9001`。
- **校验顺序**：先查绑定 → 再查库存 → 再查积分（与真实平台的报错优先级一致，避免"库存不足"和"积分不足"同时成立时提示错）。
- **幂等**：上报积分带 `requestId`（由 `余额 + 待上报额` 派生的稳定串），重复上报返回「该笔积分已上报，未重复计入」。
- **异步语义**：所有接口都有模拟延迟（250–600 ms），UI 用 `busy` 态防重入。
- **库存**：按「已兑次数」记账，`已兑 ≥ 总量` 即售罄。

> 为什么花力气做这些「假接口」？因为**换真接口时只需要替换 transport 层**。这是我们给评审的工程交代：接口边界是照着真平台画的，不是随便 return 一个对象。

### 7.5 「我的树」：把数据长成一棵树

这是全项目最容易被记住、也最容易被问「怎么实现的」的地方。

**要解决的问题**：把累计减排映射成一棵看得出「长大了」的树。难点是——树必须**每次长得一样**（同一份数据不能每次刷新都变形），但又必须**看得出生长**。

**做法**：

1. **确定性伪随机**：所有抖动都由种子（记录序号 / 因子 id 的哈希）驱动，同一份数据重绘结果完全一致。这是它可测试的原因（`RoughMath` 是纯 TS，Node 里能断言）。
2. **树干用递归分枝**：从底部向上，每级分叉角度与长度按累计减排量缩放。
3. **叶子锚点取「整条枝上的点」而不是末梢**：v2 只在枝末端撒点，结果点全挤在外圈，渲染成「花环」而不是树冠。现在沿每根枝按比例撒点，树冠才有体积。
4. **Canvas 自绘而非组件拼装**：用 Rect + rotate + position 拼枝干，每个子节点各自旋转，结果渲染成三棵重叠的树。Canvas 一次画完才正确。
5. **点云数量与累计减排挂钩**，颜色用墨绿系，少量朱砂点做「今年的新叶」，与印章同色系。

> **被问「这棵树有什么用，是不是装饰」**：
> 「它是本项目的核心可视化隐喻：数据不是被读出来的，是被看见的。用户看到树冠变密，比看到 20.58 这个数字更有感觉。而且它的每个点都能追到一条真实记录——树冠密度就是累计减排量。」

### 7.6 图表：为什么关掉一切交互

用 `@ohos/mpchart` 封装了折线、柱状、环形三种。三条自制规则：

- 折线带**上期幽灵线**（虚线、更浅），且「上期全 0 不画」——否则会出现一条贴底的假线，比没有更误导。
- 柱子**纯色不带渐变**（`Fill` 传两个相同色标），因为柱代表「量」，渐变会造出虚假的体积感。
- 右侧 Y 轴直接关掉（与左轴刻度相同，纯噪音），X 轴用业务标签而不是索引，竖网格线不画。

> 有个坑值得讲：mpchart 的 `Fill` 只传一个色标**不报错**，但柱子会画成纯黑。这是我们实测踩出来的。

### 7.7 性能：从 O(天数 × 记录数) 到 O(记录数)

看板原来按「每一天」调一次 `behaviorsBetween`，月视图 30 次、年视图 12 次，每次底层全量扫一遍 KV；加上上期幽灵线和 12 周热力图后调用会翻到 90+ 次。

改法：**一次性把所有记录读进内存，按日期分桶**，之后所有统计（折线、热力图、目标环、区间合计）都在内存 Map 上做。

另外 `collect()` 改为**每批 8 个并发读**（`Promise.all`），而不是一条一条 `await`——记录上百条时首屏刷新从「十几个来回」降到「几次批量」。

## 9. 评委必问 48 问（按危险程度排序，前 12 条必须背熟）

### 第一梯队：答不好会直接扣分

**Q1 你们这跟市面上的碳足迹 App 有什么区别？**
> 三个区别。第一，**可核**：14 条因子每条都有基准情景和公开出处，应用内可查，还写明我们放弃了哪个口径；第二，**可感**：减排量转译成「棵树·年」和积分，看板那棵树随数据长大；第三，**不出机**：端侧推理 + 本地分布式 KV，全链路无云端。同类作品大多只做到「能算」，没做到「算得清、看得见、信得过」。

**Q2 减排量是怎么算的？举一个例子。**
> `ER = AD × (EF_baseline − EF_activity)`。以步行 6 公里为例：基准是燃油小汽车 0.19567 kgCO₂e/车·公里，步行本身排放为 0，所以每公里减排 0.19567，6 公里 = 1.17 kg。发积分按 1 kg = 100 分，即 117 分。

**Q3 数据从哪来的？可靠吗？**
> 四级优先：CPCD（中国本土）→ 生态环境部公告（省级电网因子）→ DEFRA（中国没有的条目）→ 学术报告。每条因子的 `source` 字段写着出处，应用内可展开。**并且我们标注了口径边界**：出行基准按单人驾车、电网因子用河南省级值、4 条回收因子是英国口径。

**Q4 你这个 AI 是真用了深度学习，还是调了个接口？**
> 真的在端侧跑模型：MobileNetV2 经 MindSpore Lite 推理，11.4 MB 随包，自检页能看到真实 top-5 输出。但我要如实说：分类标定表现在是空的，因为需要真机实拍照片建类别中心，模拟器喂不了这类样本，所以当前业务走 OCR 关键词兜底。这是有意的降级——填表后视觉通路自动生效，业务代码不用改。

**Q5 用户凭什么坚持记？**
> 三层反馈：即时（记完立刻看到减排量与积分）、中期（今日任务与连续天数）、长期（树长大、年度报告、可兑换权益）。核心是**把抽象数字换成有体感的参照**：1.1 棵树·年、2058 分能换地铁券。

**Q6 数据安全怎么保证？**
> 数据只在设备与同账号可信设备之间同步，**不上传任何服务器**。KV 用系统分布式存储，安全等级 S1。我们也说明白：目前没开加密（`encrypt: false`），如果要承载更敏感的数据，这是必须补的一环。

**Q7 为什么用 ArkTS 原生而不是 Flutter/小程序？**
> 三个硬需求只有原生给得到：分布式 KV（跨设备免登录同步）、桌面卡片、端侧 AI（MindSpore Lite + Core Vision Kit）。跨端框架这三样都得绕道服务端，那就违背「数据不出机」。

**Q8 你的「创新点」到底新在哪？**
> 不在单点技术，在**组合**：把碳核算的严谨性（因子溯源与口径说明）、账本的视觉语言、端侧 AI 预填、可核的积分闭环拼成一个完整体验。单看每一项都有先例，但「可核 + 可感 + 可兑 + 不出机」同时成立的，我们没找到。

**Q9 跨设备同步怎么做的？冲突了怎么办？**
> LWW + origin 兜底：比写入时间戳，相等时比设备标识，保证两端收敛到同一结果；自己的回声写入直接短路。**边界**：分布式 KV 没有事务，跨设备同时兑换仍可能超卖，真正解法是服务端幂等键，我们没假装解决。

**Q10 你这个项目最大的技术难点是什么？**
> 分布式 KV 的确定性收敛 + 端侧推理的资源管理。前者是真难：异步、无事务、会回声、时钟不可信；后者容易被忽略：PixelMap 会被就地修改导致 OCR 崩、ImageSource 不 release 会持续泄漏。

**Q11 有没有实测数据？**
> 逻辑层 55 条断言全绿；互斥锁 50 并发零丢更新并有反证；图标 24 个视觉重量极差 0.34%；全量源码经静态审查无 console/TODO/空 catch。性能上，看板统计从「按天调用 90+ 次全量扫描」改成「读一次内存分桶」。

**Q12 如果给你三个月继续做，你做什么？**
> 三件事：① 端侧标定——采 200 张真机照片，把视觉通路真正打开；② 城市碳普惠接真接口——transport 层已隔离，替换即可；③ 跨设备一致性的服务端补偿——幂等键 + 对账任务。

### 第二梯队：专业追问

**Q13 为什么减排量能是负数？** → 不会。活动量必须 >0，因子都是正差值；输入非法时预览显示「—」。
**Q14 积分能无限发吗？** → 不能。积分只能由减排行为产生，且删除记录会冲正；余额不足时扣减被拒绝。
**Q15 用户能不能伪造记录？** → 能，这是所有个人碳产品的共同问题。我们的态度：不假装有防伪，而是用「凭证」给正向用户一个可分享的凭据，用规则约束（每日上限、撤销留痕）。真正的防伪需要硬件或平台侧核验。
**Q16 你的「减排凭证」是什么？** → 一张把当日/当月减排、连续天数、印章式图章合成的可保存图片，用于分享，不含个人信息。
**Q17 年度报告怎么算的？** → 按记录年份聚合：记录条数、活跃天数、累计减排、主力贡献（占比最高类目）、全年积分；跨年数据按 `date` 字段分年。
**Q18 8 篇科普写了什么？** → 分政策、概念、数据、技巧四类，把「碳中和是什么」「碳普惠怎么运作」「为什么是 0.5897」讲清楚。
**Q19 桌面卡片怎么刷新的？** → 记账成功后主动 `updateForm` 刷新；刷新失败被单独 catch，不影响记账结果。
**Q20 为什么不用 Room/关系型数据库？** → 碳数据天然是键值 + 列表，分布式 KV 直接给了跨设备同步；关系型的联表能力在这里用不上，还会让同步变复杂。
**Q21 数据导出格式是什么？** → JSON 全量备份（带 `schema: carbon-footprint/v1` 版本号）+ CSV 明细（便于 Excel 做表）。
**Q22 为什么 CSV 导出要在 UI 线程写？** → 这是已知待优化项：小数据量没问题，记录多时应该挪到 TaskPool。我们把它列为技术债而不是假装没有。
**Q23 你的设计为什么这么「素」？** → 见第 2 节论证链：账本的心理模型要求可信、留痕、私密，卡片流会把连续数据切成资讯流。
**Q24 朱砂红为什么只占 2%？** → 它是印章色，是「确认」的符号，不是装饰色；大面积使用会把它变成普通强调色，符号性就没了。
**Q25 无障碍考虑了吗？** → 部分：对比度按深墨/纸底设计（正文对比度 > 7:1），数字用等宽字体；但**没有做完整 TalkBack 标签体系**，这是已知缺口。
**Q26 你这个「树」是图片还是代码画的？** → 纯 Canvas 代码绘制，无图片资源；抖动由种子驱动，同数据同结果。
**Q27 为什么同一份数据每次刷新树形一样？** → 伪随机种子来自数据本身（记录 id 哈希），不是时间。
**Q28 你用了第三方库吗？** → 只有 mpchart（图表）。图标、树、印章全部自绘，避免视觉不一致。
**Q29 为什么图表不能交互？** → 它是信息图不是分析工具；固定视野才能保证「一页账」的稳定阅读。
**Q30 你的错误处理策略？** → 分层：KV 层统一包 Error 抛出，业务层决定降级（订阅失败→本机模式）或提示（保存失败→提示重试），UI 层不吞异常。
**Q31 冷启动慢怎么办？** → 已做：字体子集化、批量并发读、首屏只读必要键。未做：首屏骨架屏。
**Q32 为什么启动失败页现在有重试？** → 因为原来只能杀进程重开，这是真实体验缺陷。

### 第三梯队：容易被问住的细节

**Q33 CPCD 是什么？** → 中国产品全生命周期温室气体排放系数库，中国本土最权威的 LCA 数据库之一。
**Q34 DEFRA 是什么？** → 英国环境、食品和农村事务部，每年发布 GHG 换算因子，国际通用。
**Q35 为什么光盘行动按餐次算？** → 餐饮浪费的减排与「浪费的食物重量 × 单位食物碳足迹」相关；用「餐次」是因为用户可感知的最小单位是「这一顿」，内部按人均浪费量折算。
**Q36 回收旧衣物为什么 22.16 kg/kg 这么高？** → 纺织品全生命周期（种植/化纤生产 + 加工 + 运输）碳足迹高，回收替代原生纤维的减排量因此很大。这是国际文献常见量级。
**Q37 你们的积分和真实碳普惠平台的积分能互通吗？** → 不能，目前是本地模拟。但接口语义（错误码、幂等、库存）对齐真实平台，为将来对接留了口子。
**Q38 为什么地铁因子取 43.14 而不是 8.81？** → 量级校验：43.14 与京沪地铁实际、DEFRA 伦敦地铁 27.8 更吻合；8.81 明显偏离，会让地铁减排虚高。
**Q39 ArkTS 有什么限制？** → 静态类型、无 `any`、不支持部分动态特性；这对我们是约束也是收益——编译期就能挡住很多错。
**Q40 你们的测试怎么在没设备的情况下跑？** → 把纯计算模块（因子、任务、抖动几何）写成不依赖 ArkUI 的 TS，用 Node 直接跑。
**Q41 为什么用单例仓库？** → 全局共享一份内存缓存与锁；并发初始化用 in-flight Promise 收敛，避免建两个 store。
**Q42 你怎么保证删除记录后账对得上？** → 冲正而非删除：写一条负数流水，撤销额不超过当前余额，`balanceAfter` 全程算术自洽。
**Q43 双击兑换会扣两次吗？** → 不会。UI 层 `busy` 态 + 数据层互斥 + 余额保护三道。
**Q44 如果 KV 写失败会怎样？** → 抛错给业务层；行为记录与积分要么都成立、要么都不成立（补偿删除）。
**Q45 你们的 App 有多大？** → 安装包主体 + 11.4 MB 模型 + 546 KB 字体子集；模型是端侧能力的前提，我们接受这个体积。
**Q46 为什么不做排行榜？** → 碳数据社交化必然引发攀比与伪造；我们选择私密 + 自我对比（上期幽灵线）。
**Q47 这个项目可复制吗？** → 因子库与口径论证是可复用的方法论；端侧 AI 与分布式同步是可复用的工程骨架。
**Q48 你们团队怎么分工的？** → （按实际答，此处不代写。）

## 11. 高危问题与话术边界

| 高危问题 | 错误答法 | 正确答法 |
|---|---|---|
| 「你的 AI 真的在跑吗」 | 含糊说「用了深度学习」 | 见 Q4：模型真、链路真、标定表空、走 OCR 兜底 |

| 「有防伪吗」 | 说「有防作弊」 | 说「没有，这是个人产品的共同问题，我们的态度是……」 |
| 「和 XXX 比怎么样」 | 贬低别人 | 只讲自己的三个区别，不评价他人 |
| 「这个功能是不是没做完」 | 辩解 | 「是边界，不是遗漏，原因是……下一步是……」 |
